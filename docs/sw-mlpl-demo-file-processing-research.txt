That fits the philosophy already established by demo-memory: make an honest runnable approximation where possible, identify precisely what cannot yet be expressed, and turn each blockage into an earned upstream capability request. demo-memory explicitly follows that model.

I would create demo-binary-files
I prefer that over something audio-specific such as demo-audio, because the capability being tested is much broader:

demo-binary-files
The progression could eventually cover:

bytes → bits → fields → records → chunks → streams → containers → codecs
That gives you applications involving audio, images, archives, executable formats, model formats, network captures, etc. MP3/Ogg then becomes one particularly demanding vertical slice rather than defining the repository.

This is especially appropriate because you've already reached an interesting boundary in demo-memory: MLPL has fixed-width bit operations including masking, shifts, Boolean operations, popcount, and bit-vector conversion, but the values are still exact integer-valued f64s. Packed physical storage is explicitly still missing.

So this new demo can pick up almost exactly where demo-memory stops.

But I would not start with MP3 → Ogg
MP3→Ogg is a good ultimate demo, but a poor first forcing function.

A transcoder is roughly:

MP3 file
   ↓
MP3 container/frame parser
   ↓
MP3 Huffman/bitstream decoder
   ↓
frequency-domain reconstruction
   ↓
PCM audio
   ↓
Vorbis/Opus encoder
   ↓
Ogg packetizer
   ↓
Ogg file
Only the outer layers are primarily file/bit manipulation.

The middle is substantial signal-processing and codec work.

If you implement the whole thing in MLPL, you've accidentally turned the experiment into:

"Can sw-MLPL implement two sophisticated audio codecs?"

rather than:

"Can sw-MLPL conveniently process real binary files?"

That's eventually valuable, but it muddies the forcing signal.

Instead, I suggest a staged architecture.

Stage 1 — make binary files first-class
Start with something as mundane as:

demo-binary-files/

        ogg/
        wav/

        mp3.mlpl

The very first demo should be an MLPL hexdump.

For example, conceptually:

bytes
|> chunks(16)
|> each(format_hex)
|> print
That sounds trivial.

It is exactly the kind of trivial application that will expose whether the language has the right low-level substrate.

You immediately discover whether you have satisfactory answers for:

binary open/read/write

byte arrays

EOF

streaming

chunking

offsets

integer formatting

byte→integer conversion

avoiding f64 expansion

large-file processing

That is a much cleaner forcing function.

Stage 2 — binary field extraction
Next make MLPL pleasant for operations like:

byte 0
bits 7..5
bits 4..3
bits 2..0
MP3 is excellent for this because MPEG audio frame headers are compact bitfields.

A frame starts with fields conceptually like:

sync             11 bits
version           2 bits
layer             2 bits
protection        1 bit
bitrate_index     4 bits
sample_rate       2 bits
padding           1 bit
private           1 bit
channel_mode      2 bits
...
That is an almost ideal MLPL demo.

You could express something like:

header = read_u32_be(stream)

frame = {
    sync:        bits(header, 21, 11),
    version:     bits(header, 19, 2),
    layer:       bits(header, 17, 2),
    bitrate:     bits(header, 12, 4),
    sample_rate: bits(header, 10, 2),
    padding:     bit(header, 9)
}
Notice that this is not particularly APL-like.

I think the more interesting MLPL expression would be to make the format description data:

fields = [
    ["sync",        11],
    ["version",      2],
    ["layer",        2],
    ["protection",   1],
    ["bitrate",      4],
    ["sample_rate",  2],
    ["padding",      1],
    ...
]

header |> unpack_bits(fields)
Now you're back in MLPL territory:

binary parsing as array transformation.

That could become a very attractive language demonstration.

The extension boundary I would want
Something roughly like:

decoder = mp3_decoder(open_bytes("song.mp3"))

pcm_chunks =
    decoder
    |> decode_chunks

pcm_chunks
|> map(normalize)
|> vorbis_encode({quality: 5})
|> write_bytes("song.ogg")
You don't necessarily need objects if they don't fit MLPL.

It could instead be functional:

input = file_open_read("song.mp3")
output = file_open_write("song.ogg")

state = mp3_decoder_new(input)

decode_pcm(state)
|> each(vorbis_encode)
|> each(file_write(output))
Eventually I'd aim for something cleaner like:

"song.mp3"
|> audio_decode
|> audio_encode("vorbis")
|> file_write("song.ogg")
but only after the low-level demos exist.

Otherwise the abstraction hides precisely what you're trying to test.

What this should force into sw-MLPL
I see roughly three tiers.

Tier 1: MLPL language/runtime primitives
These are fundamental enough that I would put them upstream rather than hide them in an audio extension.

1. A real byte-buffer type
This is the biggest one.

Today, packed bit algorithms can run over integer-valued f64 arrays, but the existing upstream contract explicitly says packed storage remains unresolved.

For file processing you really want something like:

bytes
backed by Rust:

Vec<u8>
or perhaps a generalized typed array:

array<u8>
array<i16>
array<i32>
array<f32>
array<f64>
That would have value far beyond binary files.

It immediately helps your ML work too:

u8   quantized tensors
i8   quantized tensors
i16  PCM
f16  model tensors
f32  model tensors
So binary files may be the forcing function that finally earns typed arrays.

That's a particularly productive outcome.

2. Streaming file I/O
I would avoid a simplistic:

read_file(path)
as the primary interface.

You need:

open
read
read_exact
write
seek
tell
close
but MLPL should probably expose a more compositional layer too:

file_chunks(path, 65536)
Then:

file_chunks("huge.bin", 65536)
|> each(analyze)
|> reduce(combine)
That is exactly where an array/functional language should shine.

3. Integer endian operations
Useful primitives:

u16_le
u16_be
u24_be
u32_le
u32_be
u64_le
u64_be
plus serialization:

put_u16_le
put_u32_be
I would implement these as a library on top of bytes where practical.

4. Bitstream reader/writer
This is slightly different from bit operations.

You currently have word-level operations such as band, bor, shifts, masks, and popcount.

Codecs need:

read_bits(1)
read_bits(3)
read_bits(11)
read_bits(17)
across byte boundaries.

I'd initially make this an MLPL library:

bit_reader(bytes)
read_bits(reader, n)
and see whether the ergonomics justify a native implementation.

Things that should not become language keywords
I'd be conservative here.

Don't add:

read_u32_be
crc32
mp3_frame
ogg_page
as language features.

Those belong in libraries.

Likewise:

bits
bytes
file
stream
may deserve core runtime types/functions, but:

MP3
Vorbis
Ogg
ID3
definitely should not.

This demo should test whether small general primitives compose into specialized functionality.

That is exactly the kind of completeness story you're trying to build for MLPL.

A generalized binary-layout library could be the real prize
I'd seriously consider whether this demo eventually produces something analogous to Python's struct, but more array-oriented.

For example:

Then:

decode(mpeg_header, bytes)
returns a record.

And:

encode(mpeg_header, record)
produces bytes.

Now consider what else this handles:

This creates a surprising bridge between several things you're already exploring.

The same infrastructure underlying:

That's a very good sign architecturally.

Worked for 25s
You are right that binary is too overloaded here. There are two distinct capabilities worth forcing:

Binary data processing — bytes, bitfields, files, streaming, array-oriented transforms.

Native executable production — turning an MLPL application into a standalone OS executable.

And the good news is that the second capability is already substantially implemented, though not yet broadly enough for something like mp3-to-ogg.

Where sw-MLPL is today on native executables
Current sw-MLPL has a real compile path, not merely a bundled interpreter. The documented command is:

mlpl build foo.mlpl -o foo
and it produces a native executable. There is also an mlpl! procedural macro for embedding MLPL inside Rust.

The architecture today is approximately:

foo.mlpl
   │
   ▼
MLPL lexer/parser
   │
   ▼
MLPL AST
   │
   ▼
lower-to-Rust
   │
   ▼
generated temporary Rust crate
   │
   ▼
cargo build --release
   │
   ▼
native executable
Most importantly, the resulting executable does not contain the parser or interpreter. It links the compact compiled runtime (mlpl-rt, mlpl-array, mlpl-core) instead.

So the preferred architecture you described—actually compile MLPL into something Rust-like—is already the direction the project took.

That is much better than:

[MLPL source] + [REPL executable] + bootstrap wrapper
although that latter approach could still be useful as a fallback packaging mode.

The limitation: the compiler currently handles a subset
The compiler is presently closer to a numeric kernel compiler than a general-purpose application compiler.

It lowers things including:

array/scalar literals
arithmetic
broadcasting
iota
reshape
transpose
reductions
matmul
dot
exp/log/sqrt/abs/pow
sigmoid/tanh
labeled shapes
but many general-purpose constructs are explicitly not lowered yet, including for, repeat, loaders/datasets, much of the ML runtime, and numerous higher-level operations.

For mp3-to-ogg, the bigger issue is that the current build mechanism is also intentionally simple: it generates a tiny Rust main() around the lowered MLPL and prints the resulting scalar.

So today:

mlpl build numerical-demo.mlpl
is real.

But:

mlpl build mp3-to-ogg.mlpl
./mp3-to-ogg input.mp3 output.ogg
is not yet the kind of application surface the compiler was designed to support.

That makes this new demo an unusually good forcing function.

What mp3-to-ogg would force into the compiler
This is where the project becomes particularly useful.

You wouldn't merely discover missing file APIs. You'd discover missing compiled-language application features.

The first set is basic control flow. The compiler currently doesn't lower constructs such as for and repeat.

A streaming codec application will quickly need:

while input remains:
    read chunk
    process chunk
    write chunk
Whether MLPL spells that as while, recursion, a stream combinator, or each over a lazy sequence is a language-design decision.

For an APL-inspired language, I'd strongly resist immediately adding conventional imperative machinery just because Rust has it.

A better target might be:

file_chunks(input, 65536)
|> each(decode)
|> each(transform)
|> each(encode)
|> write_chunks(output)
That keeps the forcing function aligned with MLPL's identity.

Command-line applications are another earned capability
A real standalone application needs at least:

argv
stdin
stdout
stderr
exit status
Potentially MLPL should expose something as simple as:

args()
returning strings.

Then:

input  = arg(0)
output = arg(1)
or an array-oriented equivalent.

The compiled runtime would implement those directly using Rust std::env::args.

This is a small feature, but it makes an enormous difference in the claim:

sw-MLPL programs can be ordinary command-line tools.

Then comes I/O
For both interpreted and compiled execution, I would want the same conceptual APIs:

read_bytes(path)
write_bytes(path, bytes)

open_read(path)
open_write(path)

read_chunk(stream, n)
write_chunk(stream, bytes)

seek(stream, offset)
tell(stream)
The important architectural rule should be:

The MLPL program should not know whether these calls are executing through the interpreter or through generated Rust.

For example:

read_bytes
would have two implementations:

Interpreter
   ↓
evaluator builtin
   ↓
Rust file implementation
versus:

Compiled MLPL
   ↓
generated mlpl_rt::read_bytes(...)
   ↓
same Rust file implementation
That preserves interpreter/compiler parity.

This suggests an important refactoring principle
Anything intended to work in compiled MLPL should ideally not be implemented exclusively inside the evaluator.

Instead:

                ┌─ interpreter evaluator
MLPL operation ─┤
                └─ generated Rust
                        │
                        ▼
                  shared mlpl-rt
So file I/O, byte buffers, CRC, codec bridges, etc. should be runtime capabilities whenever practical.

That will prevent the compile path from perpetually lagging the interpreter.

  │

  │

Pure MLPL

Then the demo shows that these compose naturally.

That is exactly what a general-purpose language should permit.

Typed arrays become even more important once compilation enters the story
Our earlier discussion about u8 becomes stronger here.

For interpreted MLPL, representing bytes using exact integer-valued f64s is wasteful but survivable for tiny demos.

For a compiled command-line program processing a 2 GB file, it becomes indefensible.

The compiled runtime should eventually have representations such as:

Array<u8>
Array<i16>
Array<i32>
Array<f32>
Array<f64>
or whatever syntax/semantics you settle on.

Then MLPL's array operations could potentially operate directly on them:

samples : i16[...] = ...
abs(samples)
reshape(samples, ...)
window(samples, ...)
and the compiler lowers those into corresponding Rust typed buffers.

That is a much more important general-purpose enhancement than merely adding a read_file() builtin.

The especially attractive target
I'd eventually want this:

input = args()[0]
output = args()[1]

input
|> file_chunks(65536)
|> mp3_decode
|> map(audio_transform)
|> vorbis_encode
|> write_chunks(output)
followed by:

mlpl build mp3-to-ogg.mlpl -o mp3-to-ogg
producing:

mp3-to-ogg
with no MLPL source, parser, REPL, or interpreter needed at runtime.

That is consistent with the compiler architecture you already have rather than requiring a new architecture. The work is principally about expanding lowering coverage and the compiled runtime surface. The existing compiler documentation explicitly positions mlpl build as the case where “the MLPL is the program.”

I would therefore revise the demo roadmap
The forcing sequence becomes two-dimensional:

Demo	Data capability	Compiler capability
hexdump	byte input	CLI args + output
byte histogram	array operations on bytes	typed array lowering
WAV inspector	endian fields	records/functions
WAV copy	binary output	file APIs
huge-file histogram	streaming	compiled streaming

That makes the repository much more consequential.

The final success criterion is not merely:

“We managed to parse an MP3.”

It's:

“We wrote a practical file-processing utility in MLPL, exploited array-language operations where they made sense, streamed data larger than memory, used optimized Rust components where appropriate, and compiled the MLPL application into an ordinary standalone native executable.”

That is a compelling demonstration of general-purpose-language completeness.

And because mlpl build already exists and already avoids embedding the interpreter, I would not invest much in the bootstrap/wrapper approach except as a temporary compatibility mode. The stronger path is already there; this demo should pressure it from its present numerical subset toward a genuine application compiler.
